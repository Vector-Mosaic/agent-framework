# Instructions

This index routes the complete framework, practical guidance, repository
conventions and specialized methods. Their scopes differ. The framework applies
to human-agent work generally; repository conventions govern this toolkit and
explain their conditional use in adopting projects.
A document's location does not extend its permission or redefine another owner's
meaning. [Repository AGENTS](../../AGENTS.md) carries immediate conduct and
applicability triggers; [native delivery](../ops/codex_instruction_delivery.md)
owns how the general home carrier reaches a task.

Use the entrance that fits the actual need, or read a known exact owner directly.
This is not a required sequence, an exhaustive taxonomy or an authority-ranking
checklist. Read enough of the full explanation and its relevant relationships to
avoid a consequential misunderstanding; stable grounded knowledge is reusable.

The practical guides explain application and meaningful examples; they do not
replace complete conceptual definitions or require every example to match a task.
Shared conventions apply at the scope where consistency is useful. Specialized
methods retain their exact applicability and claim boundaries. No extra ritual,
record, protocol or validator follows merely from a method being available.

## Other sources keep their own jobs

| Question | Source |
|---|---|
| What is this company, product, program or repository intended to achieve? | [North-star discovery](../north_star/INDEX.md), then the actual full purpose owner. |
| What does a system mean and how should it behave? | The adopting project's INDEX/Vocabulary and appropriate Architecture, Behavior, Contracts and other complete owners, with roles defined by [system documentation](repo_organization/system_documentation.md). |
| What implementation and configuration exist? | Actual code, component/native manifests, configuration and executable entrypoints. |
| What works or happened within a particular scope? | Applicable tests, runtime observation, Git and meaningful retained evidence. |
| How is an included operation performed against its actual target? | [Documentation index](../INDEX.md), [setup](../setup.md), applicable operation guides and tool usage. |
| Which account is selected and where is its owned access? | User-local account references and [credential custody](../credentials.md). Presence does not prove authorization or live access. |

Accepted documentation is authoritative for its actual intended meaning, not
proof that code exists or a deployment works. Implementation accidents do not
silently revise intent. Evidence reaches only the claims and conditions it
supports; strong warranted conclusions are appropriate without defensive
bookkeeping. Resolve a material conflict at the competent owner instead of
flattening these sources into one universal precedence list.

## Maintain one coherent set of owners

General definitions and relationships live in the framework; applied agent work
belongs in the practical guides. Repository conventions own their concrete
shared choices, systems own their meaning and behavior, and operations own exact
execution knowledge. Keep complete meaning at one appropriate owner and use
ordinary Markdown routes instead of independently maintained copies.

Change accepted meaning only within covering authority. Update affected routes,
consumers, examples and native entry conduct with the owning change; remove
obsolete rules and superseded containers. Existing system contracts, meaningful
evidence, security/access mechanisms and operational tools are not discarded
because a general policy document is retired. Do not recreate removed authority
matrices, instruction validators, generic review loops or archival pointer files.
Useful rationale stays with its actual owner; there is no general mandatory ADR
apparatus. [Maintaining the layer](practice/maintaining_the_layer.md) explains
coherent change and delivery responsibilities.
